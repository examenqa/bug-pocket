## Concrete recipient replacement route to validate

Propose a recipient-controlled AppX repack, preserving the existing executable/ASAR and startup bridge. A DLL beside an EXE inside WindowsApps is insufficient evidence: package contents are read-only and Store packages enforce integrity. This proposal does not change the current trial package or require the publisher's private signing key. It remains untested and subject to the owner's LGPL/Store interpretation. [Package filesystem](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes#installation) · [Package integrity](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview#package-integrity-enforcement).

1. Supply a recipient-readable copy of the exact release AppX payload and the source/build materials above. Test acquisition from the actual Store-recipient route; the current unsigned trial is not proof that Store customers can obtain that input. Use a disposable Windows VM/snapshot with no staged, provisioned or registered `ExamenQA.BugPocket` for any user, a disposable account and fresh synthetic data. A second account on a machine retaining the same package identity is insufficient isolation because package staging is shared. Keep the original Store installation/data intact on the original machine.
2. Recipient builds an x64 ABI-compatible modified `ffmpeg.dll` from the supplied materials, retains licence/change notices and records its distinct SHA-256. Use a benign identifiable change in an enabled path (for example a logged decoder initialization message) that preserves exported names, ordinals, calling conventions and Chromium-required behavior. A hash change alone does not prove the replacement executed.
3. `MakeAppx unpack /p <release.appx> /d <fresh-layout>`; replace only `app/ffmpeg.dll`. Construct a payload-only packing layout containing the original manifest/assets/app files, excluding old `AppxSignature.p7x`, `AppxBlockMap.xml`, `[Content_Types].xml` and package footprint metadata so MakeAppx regenerates them. Retain all notices/native resources. Record the exact input/output file map and byte comparison; no WindowsApps patching or ACL bypass.
4. Keep manifest Name `ExamenQA.BugPocket`, Publisher `CN=8D9BF560-2073-427E-9DB1-92BB6AB1F379`, Application Id `BugPocket` and `Enabled=false` startup declaration. `MakeAppx pack /d <payload-layout> /p <recipient.appx> /no` with semantic validation. The recipient creates and trusts their own local test signing certificate with the matching manifest subject, then signs and installs their package only in the clean disposable VM/account. They do not need Examen QA's private key for this proposed local re-signing step. Matching the manifest subject is a necessary signing condition; it does not remove signer/content conflicts with an already staged Store package or prove deployment will succeed. Prove actual signature validation, clean deployment and absence of identity conflict, recording the OS version, certificate thumbprint, package identity and deployment receipt. Signing/trust changes need their explicit informed approval and cleanup. [MakeAppx](https://learn.microsoft.com/en-us/windows/msix/package/create-app-package-with-makeappx-tool) · [Subject matching and local trust](https://learn.microsoft.com/en-us/windows/msix/package/create-certificate-package-signing).
5. Activate the repackaged AUMID, confirm Windows-loaded module path/hash plus the observable modified enabled-library behavior, and test startup, renderer, image capture/display/annotation/export and graceful quit. The real bridge hardcodes this package family/AUMID in `native/store-startup/store_startup.cc`; simply inventing a new identity would make startup identity verification fail. Verify normal Store opt-in/read behavior with the preserved identity, without assuming it from successful repacking.
6. Uninstall the recipient test package and remove only the certificate/trust entries created for the exercise, or revert the disposable VM snapshot after retaining evidence. Preserve the original machine's Store installation and all original evidence/data. Document that recipient test certificates can conflict with Store update/reinstallation; do not install over a Store registration. VM availability, clean package-store checks and the approved validation environment are additional prerequisites to this proof.

For use on the recipient's original device, there is no demonstrated safe coexistence with an existing same-identity Store installation. An acceptable documented path may require a verified backup/export of only the recipient's own data, a controlled unregister/uninstall of the original with their informed approval, and resolution of all other-user registrations, shared staging/provisioning and signer conflicts before installation. Do not silently remove another user's registration or globally deprovision the app. Rollback must remove only the recipient's derivative/trust and reinstall the original from the Store, restore their backed-up data, and verify startup/update behavior. Acquisition/reinstall availability, data compatibility and the cost or feasibility of these steps are unresolved. A VM-only developer proof does not by itself establish a practical replacement route for every Store recipient on their own device.

The preferred legal theory is a suitable shared-library mechanism under LGPL 2.1 §6(b), coupled with complete library source under §4. Test the recipient's actual ability to build and run a compatible modified library, and obtain owner/legal confirmation that the repackaging/access/trust requirements satisfy §6 for Store recipients. If §6(a) is selected instead, identify and deliver the work's machine-readable source/object material needed for relinking, including Electron/Chromium and application pieces and required build utilities. The current app ASAR and general source links alone do not establish that alternative. An unpackaged companion could avoid package signer conflicts, but is not offered as a completed substitute: it loses Store package identity/startup-task behavior, changes startup and update routes and may share ordinary-profile paths unless isolated. Its feature impact, safe profile/data handoff and native/image/startup/update validation would require a separate substantial proposal before implementation.

The Store developer agreement leaves FOSS compliance with the publisher and permits publisher customer terms. Its default customer restrictions need reconciliation with the LGPL allowance above. Review the actual accepted agreement and shipping terms before submission; no organization was contacted. [App Developer Agreement v8.11 §§4(b), 4(c), 4(i), Exhibit G](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/store/documents/legal/ada/fy26/MS.Store.ADAv8.11.US.EN.pdf).
