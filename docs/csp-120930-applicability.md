## Mapped scenario and primary evidence

The [reporter in CSP issue 823](https://github.com/w3c/webappsec-csp/issues/823) describes attacker-injected `modulepreload` followed by a parser-inserted external module for the same URL/module type. Under the example nonce/hash plus `'strict-dynamic'` policies, the preload is treated as non-parser-inserted and admitted; the later element would be denied, but reuses the document's module-map entry. Nonce/hash sources and the example `data:` URL are not independently necessary; the essential policy condition is the parser-state admission difference. The reporter also identifies `iframe srcdoc` as an execution-capable route for otherwise inert `innerHTML` injection.

Maintainer Camille Lamy says Chrome changed to recheck CSP on module-map reuse; Roberto Rodriguez agrees reuse should not bypass CSP. These statements do not establish protection in a particular Electron release. The [mapped Chromium correction](https://github.com/chromium/chromium/commit/78b1ee2b219d79a63bbfab06df84eac8517f31ce) independently references issue `515948871`: in `module_map.cc`, failed `AllowScriptFromSource` changes from counting and continuing to reporting failure with a null module and returning.

| Necessary condition for this mapped failure | BugPocket source finding |
| --- | --- |
| Effective script policy admits the preload because it is non-parser-inserted, while denying the later parser-inserted module (`'strict-dynamic'`). | **Absent** in bundled production contexts: `script-src 'self'`; no `script-src-elem` override, nonce/hash source, or `'strict-dynamic'`. |
| A module-map entry is primed and reused for the same URL/module type, without enforcing the later denial. | Modules/local lazy imports exist; generated preloads would not establish the missing policy condition. Runtime repair is not assumed. |
| Attacker can cause the relevant executable markup/loading sequence. | Not established or required to decide the absent-policy condition. This assessment does not assert that all markup injection is impossible. |

Under the [CSP3 script checks](https://www.w3.org/TR/2026/WD-CSP3-20261027/#script-pre-request), parser metadata supplies that authorization distinction through `'strict-dynamic'`. Without it, `'self'` uses URL source matching: a source-disallowed module cannot prime the map through this preload exception; an allowed self module has no parser-insertion denial to evade. This is the source/spec-based reason for non-applicability, rather than an assumption that Vite never emits modulepreloads.
