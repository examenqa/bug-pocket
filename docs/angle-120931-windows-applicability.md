## Application configuration and Windows selection

BugPocket's main, Quick Capture and snip windows (`src/main/index.ts:245–250,333–338,802–807`) neither select a backend nor set `webgl:false`. Production source/configuration contains no `app.commandLine` graphics switches or `disableHardwareAcceleration()` call. Electron [defaults WebGL to enabled](https://github.com/electron/electron/blob/f81ca3d4f09f57667238120adacb01239d5ecd89/docs/api/structures/web-preferences.md#L56). Package launch scripts (`package.json:8–11`), login startup (`startupPreference.ts:83`) and `build/appx-startup.xml` add no graphics override. The application consumes no graphics-selection environment variable. Development `ELECTRON_RENDERER_URL` changes content source, not this backend-selection rule; dev/test harnesses do not establish production qualification.

The key selection files have identical blobs in both chains: Chromium's `gl_factory_win.cc`, `gl_display_initializer.cc` and `gpu_data_manager_impl_private.cc`, plus ANGLE's `Display.cpp`, `DisplayWGL.cpp` and `angle.gni`. Links below use the candidate revision:

## Overrides, remaining gap and qualification

Explicit `--use-angle=gles` can select `ANGLE_OPENGLES`. Windows [`Display.cpp:672–675`](https://github.com/google/angle/blob/f10470c77e4810ece55cbe8e08469a31610e92f4/src/libANGLE/Display.cpp#L672) routes this to WGL; [`DisplayWGL.cpp:242–248,811–823`](https://github.com/google/angle/blob/f10470c77e4810ece55cbe8e08469a31610e92f4/src/libANGLE/renderer/gl/wgl/DisplayWGL.cpp#L242) requires an ES-profile WGL extension and attempts an ES-profile context. This proves a conditional source route, not an affected Windows driver's existence. Native-GL overrides and custom D3D-disabled builds are outside the exclusion. `ANGLE_DEFAULT_PLATFORM` alone is not an established override here: Chromium supplies backend attributes instead of relying on ANGLE's default-display choice.

The exact remaining question for such configurations is whether a supported Windows deployment supplies a PowerVR native context with the required WGL support **and** the mapped faulty texture behavior. Source cannot settle that driver/runtime fact. No proprietary-driver investigation is proposed.

For later, separately approved qualification, use the existing QA/manual-startup method on a provenance-verified runtime to record effective launch switches, runtime tuple, and Electron's existing [`app.getGPUInfo('complete')` / `app.getGPUFeatureStatus()`](https://github.com/electron/electron/blob/f81ca3d4f09f57667238120adacb01239d5ecd89/docs/api/app.md#L1551) after GPU information is available. A D3D11/WARP/SwiftShader result supports that deployment configuration's exclusion. A native PowerVR GL/GLES result leaves driver behavior/mitigation unresolved; one machine cannot establish Windows-wide immunity. No PoC or new test infrastructure is needed for this first check.
